# 自動化利益基盤 運用OS（GROWTH_OS）

最終更新：2026年8月4日
対象：株式会社アトリエ・テクノフォルム（atelier TECNOFORM Inc.）代表取締役 江藤徳晃

## これは何か

江藤さんの指示（「業務改善とAIによる利益向上のため、新規事業も含めた自動化利益基盤を制作整備せよ」）に基づき、
次の10ステップのループを、このリポジトリの中で実際に回せる仕組みにしたもの。

1. 現在地を観測する
2. 問題の原因を推論する
3. 複数の仮説を競わせる
4. 最も有望な施策を作る
5. 別のAIに批判させる
6. ルール違反を機械的に検査する
7. 人間の承認後に実行する
8. 結果を測定する
9. 学びを保存する
10. 次の施策を改善する

**大事な前提：この10ステップのうち、AIが自律的に完結できるのは 1〜6, 8〜10 だけ。
Step 7（実行）は、お金・法務・ブランド・在庫が絡む限り、必ず江藤さんの承認を経由する。**
これは制約ではなく、この仕組みの安全設計そのもの（既存の `hero-rotation.yml` が採用している
「AIが提案 → PRを作る → マージするかどうかは人間が決める」という型を全体に拡張している）。

## 10ステップ ↔ 仕組みの対応表

| Step | やること | このリポジトリでの実装 |
|---|---|---|
| 1. 観測 | 事実を集める | `scripts/observe_growth_signals.py`（毎月自動実行）＋ `data/inquiries-ledger.csv`＋`data/relationships.json`（人が手で記録） |
| 2. 原因推論 | なぜそうなっているかを考える | `growth-system/PROPOSAL-*.md` の「原因推論」節（AIセッションが観測データを見て書く） |
| 3. 仮説を競わせる | 打ち手の候補を複数出し、比較する | 同上「競合仮説」節。impact/cost/risk/所要時間で比較表を作る |
| 4. 施策を作る | 一番有望な仮説を具体化する | 同上「採用する施策」節。コード化できるものはこのセッション内で実装する |
| 5. AIに批判させる | 別視点で弱点を探す | Agent（別セッション・別ロール）に反証を依頼し、結果を提案書に**そのまま**載せる（都合よく丸めない） |
| 6. ルール検査 | 既存ルールに違反していないか機械的に確認する | `LINEUP_PLAN.md`（ブランド規律・PSE）、`tokushoho.html`（特定商取引法表記）と照合するチェックリスト |
| 7. 人間承認後に実行 | 実際に手を動かす | GitHub の PR（コード・データ変更）。**金銭・法務・在庫・ブランドに関わる意思決定はPRにせず、提案書の承認チェックリストとして江藤さんに委ねる** |
| 8. 結果を測定する | 実行後の効果を見る | 次サイクルの `observe_growth_signals.py` の差分、および `data/inquiries-ledger.csv` の実績 |
| 9. 学びを保存する | 結果と理由を記録に残す | `data/growth-experiments.json` に追記（成功・失敗・却下の理由も含めて残す。消さない） |
| 10. 次を改善する | 学びを次のサイクルの前提にする | 次の `growth-system/PROPOSAL-*.md` を書くときに、過去の `growth-experiments.json` を必ず読んでから書く |

## 絶対ルール（Step 7 で人間承認が必須なもの）

以下は、どんなに有望な仮説でも **AIが単独で実行しない**：

- 価格・料金体系の変更
- 新規事業（レンタル、デジタル販売、ワークショップ等）の開始
- 在庫・発送・契約形態が変わる意思決定（例：販売→レンタルへの転換）
- `tokushoho.html`（特定商取引法に基づく表記）など法的表記の変更
- 外部（顧客・取引先）への一斉送信・公開投稿
- ブランドの見え方に関わる意思決定（`LINEUP_PLAN.md` の「ブランド規律」参照）

逆に、**observe（観測）・データの記録・レポート作成・SEOの機械的な軽微修正**などは
既存の `hero-rotation.yml` と同じ「PRを作る→マージで承認」の型で自動化してよい。

## サイクルの回し方（次にAIセッションが呼ばれたとき）

1. `data/growth-experiments.json` を読み、**過去のサイクルと学びを必ず先に確認する**
   （同じ仮説を「新しい発見」として再提案しない）。
2. 直近の `growth-observe.yml` の自動PR（観測レポート）を確認する。
3. 新しい仮説を作る場合は、`growth-system/PROPOSAL-YYYY-MM.md` を新規作成し、
   本ファイルの対応表の通りに 観測→原因推論→競合仮説→採用施策→AI批判→ルール検査→承認チェックリスト
   の順で書く。
4. コードやデータで実行できる部分（Step 7 の「自動化してよい」範囲）はこのセッションで実装し、
   通常のPRフローに乗せる。
5. 江藤さんの承認・判断が必要な項目は、PROPOSAL内の承認チェックリストとして明示し、勝手に進めない。
6. サイクルが一段落したら `data/growth-experiments.json` に type="proposal" のエントリを追記する
   （承認待ち・却下・実行済みのいずれの状態でも記録する）。

## ファイル構成

```
growth-system/
  GROWTH_OS.md              # このファイル（枠組み）
  PROPOSAL-YYYY-MM.md        # サイクルごとの提案書（観測〜承認チェックリストまで）
data/
  inquiries-ledger.csv       # 引き合い台帳（人が手で記入。UTMやアクセス解析より信頼できる一次データ）
  relationships.json         # 既存取引先・協業先の関係管理（実績データから抽出済み。再接点の土台）
  growth-experiments.json    # 10ステップループの実験・学びの台帳（観測サイクル・提案サイクルを追記していく）
scripts/
  observe_growth_signals.py  # Step1の自動化（月次）
.github/workflows/
  growth-observe.yml         # 月次実行 → PRで人間承認
```

## なぜ「露出」を最初の答えにしなかったか

`LINEUP_PLAN.md` には既に「真のボトルネックは露出（誰の目に触れるか）」という診断が書かれている。
今回のサイクルでは、この診断そのものを検証した（Step 5「別のAIに批判させる」の結果、
`growth-system/PROPOSAL-2026-08.md` 参照）。結論：B2B側（ザ・リッツカールトン東京、プレナス等）は
実績データ上すでに紹介・リピートで機能しており、「露出不足」は必ずしも正しい診断ではなかった。
**観測できていなかったのは「露出」ではなく「何が起きているかというデータそのもの」**——
だからこの基盤は、まず引き合いと関係先を記録するところから作った。
